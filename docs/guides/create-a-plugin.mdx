A Raven plugin implements one required method, `handle_event`. Startup (i.e. `start`) and
`shutdown` hooks are optional.

## Implement the trait

```rust
use async_trait::async_trait;
use raven_core::ChainEvent;
use raven_plugin_sdk::{
    Plugin, PluginContext, PluginMetadata, PluginResult,
};

struct BlockLogger;

#[async_trait]
impl Plugin for BlockLogger {
    fn metadata(&self) -> PluginMetadata {
        PluginMetadata::new(
            "block-logger",
            env!("CARGO_PKG_VERSION"),
            "Logs newly applied blocks",
        )
    }

    async fn start(
        &mut self,
        context: &PluginContext,
    ) -> PluginResult {
        println!("starting on chain {}", context.chain_id().get());
        Ok(())
    }

    async fn handle_event(
        &mut self,
        event: &ChainEvent,
        _context: &PluginContext,
    ) -> PluginResult {
        if event.is_applied() {
            println!("block #{}", event.block_number());
        }

        Ok(())
    }

    async fn shutdown(
        &mut self,
        _context: &PluginContext,
    ) -> PluginResult {
        println!("stopped");
        Ok(())
    }
}
```

## Register the plugin

```rust
use raven_core::ChainId;
use raven_runtime::Runtime;

let chain_id = ChainId::new(8_453)?;
let mut runtime = Runtime::new(chain_id);
runtime.register_plugin(BlockLogger)?;
runtime.start().await?;
```

The numeric value above is only an SDK example. `raven run` discovers the
endpoint's chain ID before ingestion, loads that chain's checkpoint, and
constructs the runtime. Plugins can read the ID from `PluginContext` and should
not assume chain ID 1 unless they are intentionally chain-specific.

## Observe dispatch and execution separately

`Runtime::process` returns after attempting to enqueue the event for every
plugin. Subscribe to outcomes before dispatch when the application needs each
handler result:

```rust
let mut outcomes = runtime.subscribe_outcomes();
let receipt = runtime.process(event).await?;

if !receipt.all_accepted() {
    eprintln!("{} plugin deliveries were rejected", receipt.rejected_count());
}

while let Ok(outcome) = outcomes.recv().await {
    println!(
        "dispatch {}: {} -> {:?}",
        outcome.dispatch_id().get(),
        outcome.plugin(),
        outcome.status(),
    );
}
```

The receipt describes mailbox delivery. Each `PluginOutcome` describes later
execution and arrives as soon as that plugin completes; it never waits for all
plugins to form one aggregate response.

## Return useful errors

Use the closest `PluginError` category so callers can diagnose failures:

```rust
use raven_plugin_sdk::PluginError;

return Err(PluginError::EventProcessing(
    "expected a Transfer topic".to_owned(),
));
```

## Run the included example

The SDK includes a self-contained block logger that does not need an RPC node:

```bash
cargo run -p raven-plugin-sdk --example block_logger
```

## Plugin design guidance

- Keep metadata names stable and unique.
- Match only the event variants the plugin understands.
- Keep `handle_event` bounded. Events are sequential inside one plugin, while
  different plugins run concurrently. A direct runtime caller can queue `E2`
  while your plugin awaits `E1`, but `E2` will not start until the `E1` handler
  finishes and its outcome is published. Another plugin may already be
  processing or finishing `E2`.
- Use async clients for I/O. Move blocking or CPU-heavy work to
  `tokio::task::spawn_blocking` or a dedicated compute pool.
- Expect bounded-mailbox overload and make stateful processing idempotent in
  preparation for future replay semantics.
- Return errors instead of panicking on chain data.
- Allocate external clients in `start` and release resources in `shutdown`.
- Unit-test the lifecycle with constructed `ChainEvent` values.

<Note>
    Dynamic installation and discovery are planned. Today plugins are Rust types
    registered directly with a `Runtime`.
</Note>
